## Problem Statement

Cloud devops hosts are still general-purpose servers. People boot Ubuntu or a RHEL clone, then Ansible, agents, and apt/dnf drift the machine away from whatever was audited. The new-era hosts that fixed drift (Talos, Flatcar, Bottlerocket) each gave something up: a shell, a general package set, or a vendor lock.

Blunix is a host operating system for that job. Russian Blue is the design constraint: quiet, small default install, nothing extra running. It is a devops OS, security-focused, for cloud nodes. It is fully automated: a disk layout model, a network model, and a node document are enough to build the image, boot it, and join a network. A cloud image has no installer prompts. A machine at the glass can fetch that same node document from an assigned host under `build.blunix.io`. The file on that host is ciphertext. The passphrase decrypts it on the machine and is not sent to the server. A person at the local console can choose speech, braille, or large print from the boot menu before those two prompts. The cloud default stays quiet. First boot is AI-ready: Grok, Claude, and the ChatGPT coding CLI are fetched from the vendors unless the install script is told to skip them. Those programs are not in the image. It is not a desktop and it is not a from-scratch userspace.

## Demand Evidence

None yet. No named operator, no incident, no one who would be upset if this image did not exist. Interest in "a security-focused devops OS" is not demand. Until one person can be named, this document is an architecture preference, not a product.

## Status Quo

Operators already solve this, badly, in one of three ways:

- Ubuntu LTS or Debian cloud images, plus cloud-init and Ansible. Familiar, and the node drifts the day someone installs a package.
- Rocky or Alma when an auditor wants SELinux and a RHEL-shaped STIG. The security story is inherited from Red Hat. A reskin does not add any.
- Flatcar, Talos, or Bottlerocket when the node is cattle. Drift is gone. Debugging and anything that is not a container gets harder, and Talos removes the shell on purpose.

## Target User and Narrowest Wedge

Unnamed. The wedge, once that person exists, is one cloud image that boots, runs containers, still has a break-glass shell, and can roll back an update. The glass path is the same image with speech selected first, then a hostname and a passphrase, for someone who should not have to drive a partitioner. That includes a blind operator. Demand for either path is still unnamed. This is not a package repository and not a second package family.

The smallest version someone could use this month is a qcow2 that boots under qemu, applies one signed update, and rolls it back. Nobody should pay for a mascot before that exists.

## Constraints

- Do not build a Linux From Scratch userspace. Rebuilding glibc, the toolchain, and the archive makes CVE response slower. It does not make the OS more secure.
- One package family. mkosi can build Debian or Rocky images. The builder does not care. The image definition, the MAC, and every package name fork on day one. Pick one.
- The shell stays. "Devops-ready" here means an operator can get a root shell when a node is sick. The package manager on the running host does not stay. Updates are image swaps.
- Name collision: blunix.com is Blunix GmbH (Berlin, Peter Thurner, founded 2016). They manage Debian and OpenBSD servers, ship Ansible roles, and already version their platform against Debian stable ("Blunix 13" tracks Debian 13). A distro under this name will be mistaken for that company. They may have trademark rights in the EU. If this project is that company, the family decision is already Debian and the work is productizing the host they already run. If it is not, the name has to change before a public commit.
- The owner of this effort says they own blunix.io. The project site is the static pages under `~/development/blunix.io`. Owning the .io name does not clear the .com collision.
- v1 does not claim FIPS, a STIG certification, or a desktop. Speech, braille, and large print are boot profiles on the host console. Orca and Emacspeak ride along as optional extensions. They do not turn the image into a graphical workstation.

## Premises

1. "From scratch" is the wrong unit of work. The product is the image pipeline, the signature, the update channel, and the default unit set. Debian (or Rocky) remains the package upstream.
2. Rocky versus Debian is real, and it is the second decision. The first is image versus mutable server. A mutable Blunix is a golden image with a logo. An immutable Blunix is an OS with an update story.
3. "Security focused" without a threat model is a slogan. v1 threats are: a compromised container attacking the host, a compromised update, and (later) a stolen disk. v1 does not claim to stop a malicious hypervisor or a physical attacker with the machine open.
4. Founding the identity on Rocky means the pitch is "we are RHEL-compatible." Red Hat's 2023 source-publication change showed that compatibility is politically contingent. Rocky remains a reasonable base when a contract requires a RHEL-shaped OS. It is a weak identity for a new distro, because the auditor asked for RHEL or Rocky, not for a third name.
5. Founding the identity on stock Debian and staying mutable loses to Ubuntu, which already has the cloud images, the tutorials, and the support ecosystem. Debian wins if Blunix owns the image, the update channel, and a smaller default install than Debian cloud images ship.
6. The name is free to use. Unverified. blunix.com already contradicts it. The owner says they hold blunix.io, which is a different registration.
7. Full automation is a set of models plus renderers that exit. A long-running config agent on the host (Ansible, cloud-init, a daemon that keeps rewriting /etc) puts drift back. The image build and first boot are the automation. After that, a new signed node document or a new image is how the machine changes.
8. Accessibility is the same shape of model. Five named boot profiles enable or mask Speakup, Speech Dispatcher, BRLTTY, a large console font, Orca, and Emacspeak. The regular profile leaves all of them off, so the default unit list still fits on one screen.
9. AI-ready means the install script can fetch Grok, Claude, and the ChatGPT CLI onto `/var` and then exit. The image build does not contain those programs. They are not started at boot. A missing checksum, a bad checksum, or `enabled: false` means nothing is installed.
10. A bootstrap config is ciphertext at an assigned hostname. The build passphrase exists on the machine that encrypts the file and on the machine that decrypts it. The server stores ciphertext. The plaintext is a node document. A shell script in that file is rejected.

## Approaches Considered

### Approach A: Debian immutable host image

mkosi builds a Debian stable (currently Debian 13 Trixie) GPT disk image. Boot is a signed UKI via systemd-boot. Root is read-only and verity-protected. Updates are systemd-sysupdate A/B swaps from a static HTTPS origin (systemd 262 renamed the binary toward systemd-sysupdate-update and left a compat symlink; the image should call whichever name its own systemd ships). Writable state is /var plus a declared /etc overlay. SSH stays. containerd is the workload runtime. Optional agents ship as systemd-sysext images, not as packages installed on the node.

Debian already documents this path: mkosi as the UKI and initrd generator, systemd-sysupdate as the update client, and an OBS package (uki-debian) that publishes signed UKIs. We are assembling a host image on a path Debian's systemd maintainers already use, not inventing a boot format.

Effort: L. Risk: Med. The update client and UKI tooling move quickly (the sysupdate rename is from September 2026).
Pros: Reproducible from snapshot.debian.org. No corporate source gate. Same userspace family as most containers operators already debug. Shell stays, drift goes.
Cons: SELinux is not the default MAC. AppArmor is, and Debian's profiles are less aggressive than Ubuntu's. Compliance buyers who need a RHEL STIG will say no. We own the update channel, which is a product, not a weekend.

### Approach B: Rocky compliance host

A traditional Rocky image, SELinux enforcing, OpenSCAP content derived from RHEL, dnf and Ansible as the management plane. mkosi can build this too. Rocky is a supported mkosi distribution.

Effort: M. Risk: Med.
Pros: Fastest path to an auditor who already accepts Rocky. SELinux policy and a 10-year errata horizon come free. Right answer if the first buyer fails an audit unless the OS is RHEL-shaped.
Cons: The distro's reason to exist collapses into "Rocky with our packages." Source availability depends on how Red Hat publishes RHEL sources. Image mode, if added later, wants bootc, which is a different update stack than Approach A.

### Approach C: Mutable hardened Debian

Debian's official cloud image, a sysctl and AppArmor profile informed by the server-relevant parts of Kicksecure, unattended-upgrades, and a small Blunix apt repo for the few devops pins Debian stable is too old to ship.

Effort: S. Risk: Low.
Pros: A useful VM in days. Every Debian operator already knows how to recover it.
Cons: This is a hardening profile, not an operating system. Drift returns on the first apt-get install. It does not deliver the "new era" claim.

## Recommended Approach

Approach A. A Rocky reskin cannot out-comply Red Hat, and a mutable Debian reskin cannot out-Ubuntu Ubuntu. The open slot is a signed, rollback-able cloud host with a real shell.

What would change this: a named buyer whose contract requires RHEL binary compatibility or a current DISA STIG. That buyer gets Approach B, and Blunix should not pretend to be both.

## Automation plane

The host is fully automated when four loops run with no human at the console: build, provision, update, rollback. Update and rollback are already sysupdate plus boot counting. Provision is the new scope. You named the first two inputs. The message stopped at "3.", so this draft closes the loop with a node document. If item 3 was meant to be firewall, users, or DNS, that becomes another model of the same shape and does not change disk or network. Section 6 is how a machine that has no document yet fetches one.

Models are data in git. Scripts render them into the units systemd already applies, then exit. The scripts do not call `parted`, `sfdisk`, `ifupdown`, NetworkManager, or dhclient. If a renderer shells out to those, the model has failed.

```
models/disk/<name>.yaml       partition layout
models/network/<name>.yaml    links, addresses, routes, DNS
models/access/<name>.yaml     which speech, braille, and font units this boot starts
models/ai/<name>.yaml         which vendor CLIs to fetch, pinned version, digest
models/node/<name>.yaml       disk, network, access, ai, hostname, update channel
apply/blunix-disk             layout  -> systemd-repart drop-ins
apply/blunix-net              network -> /run/systemd/network/*
apply/blunix-access           access  -> masked or started units, vconsole font
apply/blunix-ai               fetch, verify, link under /var, or remove them
apply/blunix-node             validates the node document; the others read only that
```

One schema, two moments for disk. Image build feeds the rendered repart drop-ins to mkosi, which writes the GPT. First boot runs the same drop-ins from the image so `/var` grows to the real cloud disk. The ESP and the root slots stay put. One schema, one moment for network: a generator writes units under `/run` before networkd starts. `/run` is empty after reboot, so the next boot renders again from the node document. Hand edits on the machine do not survive, which is the point.

### 1. Disk layout model

systemd-repart is already a partition model (Discoverable Partitions Specification). The YAML exists so a human can review one layout and have it drive both the factory image and first-boot grow. `blunix-disk` checks the model and emits `repart.d` files. It does not invent a partition table format.

v1 layouts:

- `cloud-vm` is the spike. ESP, root A, root A verity, root B, root B verity, `/var`. `/var` carries the only grow weight. Roots are read-only erofs. No swap.
- `metal-luks` is the same map with LUKS2 on `/var`, enrolled to the TPM with `systemd-cryptenroll`. The passphrase and the key are credentials. They are absent from the YAML. Root stays verity-protected. Confidentiality work in v1 is `/var`, because that is where node state lives.

Rules the renderer enforces, and rejects the model when broken:

- An ESP exists and is first.
- Each verity data partition names exactly one hash partition.
- Exactly one partition has grow weight.
- Sizes are explicit. No "rest of the disk" except that one weight.
- Alignment is 1 MiB.
- Unknown fields fail closed.
- No passphrase, key file, or recovery-token field is accepted in the schema.

Sketch of `cloud-vm`:

```yaml
apiVersion: blunix.dev/v1
kind: DiskLayout
name: cloud-vm
partitions:
  - name: esp
    type: esp
    size: 512M
    format: vfat
  - name: root-a
    type: root-x86-64
    size: 2G
    format: erofs
    verity: root-a-verity
    read_only: true
  - name: root-a-verity
    type: root-x86-64-verity
    size: 64M
  - name: root-b
    type: root-x86-64
    size: 2G
    format: erofs
    verity: root-b-verity
    read_only: true
  - name: root-b-verity
    type: root-x86-64-verity
    size: 64M
  - name: var
    type: var-x86-64
    format: ext4
    size: 1G
    weight: 1000
```

The sketch names this file `kind: DiskLayout`. The checker accepts `kind: Disk`. Network, access, AI, and the node document use `kind: Network`, `Access`, `AiTools`, and `Node`.

### 2. Network model

networkd is the only network stack on the image. `blunix-net` emits `.link`, `.netdev`, and `.network` units. v1 models are `dhcp-any` (match `en*` and `eth*`, DHCP v4 and v6, DNS from the lease) and `static-single` (one address, gateway, DNS list). VLANs, bonds, and WireGuard wait until those two boot a machine. A WireGuard private key, a Wi-Fi PSK, or an API token is a systemd credential named by the model. The secret bytes are not in git.

Rules:

- A model is DHCP or static, not both.
- Static requires a prefix length and a gateway.
- Match rules are explicit. A model that matches every interface including the container bridge is rejected.
- Unknown fields fail closed.
- Field names that look like key material (`private_key`, `psk`, `password`, `token`) are rejected at parse time.

Cloud metadata is a source, not a second stack. `blunix-cloud` reads the instance metadata (hostname, SSH user keys, "this NIC is DHCP") and writes a node document in this same schema. cloud-init is not installed. It is a large Python surface aimed at mutable images.

### 3. Node document

Disk and network models describe kinds of machines. The node document names one machine and points at one of each. It is the only per-host input.

```yaml
apiVersion: blunix.dev/v1
kind: Node
name: web-01
disk: cloud-vm
network: dhcp-any
access: regular
ai: default
hostname: web-01
update:
  url: https://updates.example/blunix
  channel: stable
sysexts: []
```

`blunix-node` checks that the named models exist. Once an image leaves a laptop, it also checks a signature and refuses an unsigned document. The spike may use an unsigned local file, and the image must print that it is doing so. A bootstrap decrypt has to yield this same document before anything is applied. SSH host keys and authorized user keys are credentials delivered beside the document, not fields pasted into it.

Changing a partition layout is a PR that rebuilds the image. Changing this node's address is a new node document and a reboot. Neither change is a script edited on the box.

### 4. Access profiles

Speech, braille, and large print are boot profiles. You asked for them as GRUB menu entries: full speech, console/TTY speech only, large print, regular users, advanced users. The image keeps systemd-boot, because the kernel, initrd, and command line ship as one signed UKI. With Secure Boot on, systemd-stub ignores a command line typed at the menu when the UKI already contains a `.cmdline` section. Five free-form GRUB prompts would either break that signature or become an unsigned way to change the boot. The five choices are five profiles inside one UKI. Sysupdate still ships one artifact per A/B slot. The menu lists your five names in your order. Inside the UKI, profile `@0` is `regular`, and systemd-stub boots `@0` when no profile argument is present, so a boot that skips the menu stays quiet. `@1` is full speech, `@2` is console speech, `@3` is large print, `@4` is advanced. The menu does not open an editor.

The menu itself cannot speak. Speakup starts only after the kernel is running, which is the same limit the Debian installer has. Debian's installer beeps when the menu is ready (once on BIOS, twice on UEFI) and takes a one-key shortcut so a blind user does not arrow through a silent list. Blunix copies that: a beep when the menu is ready, then keys 1 through 5 boot the five profiles. If systemd-boot cannot beep and cannot bind those keys without a fork, a one-screen GRUB menu is allowed in front of it. That GRUB only chainloads the signed UKI at the chosen profile. It does not load its own kernel, and with Secure Boot on it does not pass a free-form command line.

Factory default for a cloud image is menu entry 4, regular (`@0`), with a short timeout so an unattended VM does not sit on the menu. The last pick is remembered for the next reboot, so a blind operator is not dropped back into silence. A signed node document pins `access:` and that pin is the default entry on the next boot. A menu pick still applies to this boot. The next reboot returns to the document. On a speech profile, the machine speaks that fact.

`blunix-access` reads `blunix.access=` from the profile command line and starts or masks units. Unknown names fail closed to regular. Packages that have to talk before login ship in the image, masked, and in the initrd: Speakup (in-tree in Debian's kernel; the image loads the modules, it does not carry a second kernel), `espeakup`, `espeak-ng`, `speech-dispatcher`, and `brltty`. Emacspeak pulls Emacs, and Orca pulls a graphical session. Those two are sysexts. The base image stays a host.

| Menu | Profile | What this boot starts |
| --- | --- | --- |
| 1 | `full-speech` | Speakup soft synth, espeakup, Speech Dispatcher, BRLTTY. Orca only if the graphical sysext is installed. Emacspeak is on disk for when someone runs Emacs. It is not a boot service. |
| 2 | `console-speech` | Speakup, espeakup, Speech Dispatcher, BRLTTY. Orca stays masked even if its sysext is installed. |
| 3 | `large-print` | A 32-cell console font and `consoleblank=0`. Speech, BRLTTY, and Orca stay masked. |
| 4 | `regular` | None of the access units. Default font. This is the cloud default and the one-screen unit list. |
| 5 | `advanced` | Same access units as regular. Boot status is shown on the console. This is the entry an operator picks at the glass. |

"Advanced users" was not defined past the name. This draft treats it as the sighted operator entry: quiet services, visible boot status, the break-glass shell the host already keeps. If advanced was meant to be a synthesizer picker, a braille-only mode, or a wider set of host tools, that replaces this row and leaves the other four alone.

Rules:

- espeakup and brltty failing to find a sound card or a braille display must not fail the boot. Getty still starts. Three beeps mean speech was requested and did not come up.
- Speech Dispatcher and BrlAPI listen on local sockets only. Containers do not see those sockets.
- Full speech and console speech share one mixer, Speech Dispatcher, so a later Orca session and the console reader do not fight over the sound card.
- The graphical sysext is Wayland or X, whichever Orca on Debian 13 actually drives. The profile name stays Orca. The base cloud image does not install that sysext.
- A profile name outside the five is rejected at parse time.

### 5. AI tools

The host comes up AI-ready unless the install script is told to skip it. Ready means three vendor CLIs are on `PATH` and idle: Grok (`https://x.ai/cli`), Claude Code (`https://claude.ai`), and OpenAI's Codex CLI, which is the ChatGPT coding tool (`https://chatgpt.com/codex`). The ChatGPT desktop app is a GUI and stays out of this host.

The image build does not download them and does not copy them in. CI fails the build if a Grok, Claude, or Codex binary appears inside the UKI. What the image does ship is `blunix-ai`. First boot, after the network is up, that script reads the AI model and either fetches the pinned releases or exits because `enabled` is false. `blunix-ai disable` is the same switch from a shell. The image is identical either way. A vendor outage or a refused checksum does not stop sshd. The script records the failure and can be run again.

Each vendor's documented install is `curl | bash`, and those scripts track a "latest" channel. Claude's installer also turns on its own background update. Blunix does not run those scripts. `blunix-ai` downloads the vendor binary for the pinned version, checks it, and links it under `/var/lib/blunix/ai/`. Config and login state stay on `/var` too, because the root is read-only and the script must not rewrite a shell rc file. Vendor auto-update stays off. A newer CLI is a new version and a new digest in the model, then another run of the script.

The model names the tool, the version, and a sha256. It does not accept an arbitrary URL, so a node document cannot retarget the fetch. The script already knows each vendor's release host: `x.ai` (Grok's fallback bucket is the GCS bucket their own installer uses), Anthropic's published Claude Code manifest, and `releases.openai.com` plus the OpenAI GitHub release. Any other host is rejected. Claude's manifest carries sha256 checksums, and Anthropic publishes manifest signatures from release 2.1.89 onward, so those get checked too. Codex publishes sha256 on the release. Grok's `install.sh`, as fetched on 2026-09-29, downloads `grok-<version>-<platform>` and checks that the binary runs `--version`. It does not check a published digest. The digest in our model is still mandatory: the pin commit records a checksum a human reviewed, and every later fetch has to match it.

```yaml
apiVersion: blunix.dev/v1
kind: AiTools
name: default
enabled: true
tools:
  - name: grok
    version: "1.0.44"          # example pin shape, not a verified download
    digest: sha256:<64 hex>
  - name: claude
    version: "2.1.284"
    digest: sha256:<64 hex>
  - name: codex
    version: "0.159.0"
    digest: sha256:<64 hex>
```

Rules:

- `enabled: false`, or a tools list that omits a name, skips that fetch and removes its link.
- A missing digest, a mismatched digest, or an unknown tool name fails closed. Nothing from that run is linked.
- Field names that look like key material are rejected. `XAI_API_KEY`, `ANTHROPIC_API_KEY`, and `OPENAI_API_KEY` are systemd credentials. Browser login, when a person is at the console, writes the vendor's own auth file under `/var`.
- No systemd unit starts `grok`, `claude`, or `codex`. They are interactive programs with a shell. AI-ready is installed and idle.
- The default unit list on the regular profile still fits on one screen. `blunix-ai` is a oneshot that exits.

### 6. Bootstrap config

You own blunix.io. The public face is the static site in `~/development/blunix.io`. Account, API, and the Blunix Log are designed on that site. None of them are open. This pass does not create accounts, does not store a passphrase, and does not bind an issuer.

People sign in as a relying party. The allowlist is Authentik at adsas.id, Google, and GitHub. There is no local account password, and this platform does not run an OAuth server. The adsas.id discovery URL and the client ids are written down when those issuers are bound. Google is OpenID Connect at `https://accounts.google.com`. GitHub user sign-in uses GitHub's OAuth 2.0 authorization-code endpoints. Browser login is authorization code with PKCE. An ID token is accepted only for an allowlisted issuer, a matching audience, a live expiry, and an algorithm on the issuer's allowlist. `none` is rejected. Anything else fails closed.

The installer URL is a label the account registers: `https://{label}.build.blunix.io/`. An example is `https://ada.build.blunix.io/`. The earlier numbered draft (`ada-1042.build.blunix.io`) was a way to keep world-readable ciphertext behind an unguessable name. A name you choose and hand to an installer can be guessed. TLS authenticates the name. The passphrase authenticates the document. Anyone who can guess the label can download the ciphertext. A bearer on that fetch would be a second secret. Say if you want it.

The label assumption is one ASCII DNS label matching `^[a-z][a-z0-9-]{0,30}[a-z0-9]$`, with no punycode and with reserved names blocked (`www`, `api`, `updates`, `log`, `mail`). Lookalike labels are not rejected yet. Replace the pattern if a userid needs other characters. One account may hold many labels. Each label has one current ciphertext.

Creation, once the portal exists:

- The person signs in with one allowlisted issuer. The build passphrase is a second secret. It is never the thing the issuer checks.
- They register the label. Until a ciphertext is published, `GET /` on that host is a 404, and the installer applies nothing.
- They compose a node document in the browser. It has to pass the same schema the image already accepts. Unknown fields and key-material field names are refused before encrypt.
- They set the build passphrase in the browser. The browser encrypts with age's own passphrase mode and uploads ciphertext. age stretches the passphrase with scrypt, as the age specification defines. We do not put a second cipher around it. Debian's `age` package is the implementation on the image. The browser build has to speak that same format, and it is not written.
- The passphrase is not in the upload, is not hashed on the server, and cannot be recovered. A lost passphrase means that config is gone and a new one is created.
- Programs call the API with a key instead of a browser login. The key is drawn from the OS CSPRNG, shown once, and stored only as a SHA-256 hash compared in constant time. It is high entropy, so it is not stretched with Argon2id. A log may store that hash as a fingerprint. It must not store the key.

Publishing again replaces the ciphertext the next install will fetch. A machine that already applied a document does not poll this URL. It changes when its update channel ships a new image (section 7).

Install, on the machine:

1. The person picks the boot entry. Keys 1 through 5, same menu as section 4. A blind operator picks full speech or console speech so the later prompts are spoken. The menu beeps, because speech starts only after the kernel.
2. The system boots.
3. The first ethernet takes a DHCP lease from the `dhcp-any` model. The document that would choose a static address is the file being fetched, so this first lease cannot wait for it. This is the same network model, used before a document exists. It is not a second stack.
4. The console asks for the build hostname. On a speech profile it reads the name back and waits for a confirm before the fetch. A typo must not request someone else's host.
5. The console asks for the build passphrase with echo off. Speech announces the prompt. It does not speak the keystrokes.
6. The machine fetches `https://{host}/` and decrypts locally. TLS is for `*.build.blunix.io`. A bad passphrase reports "could not decrypt" and applies nothing. A partial document is never applied.
7. The plaintext has to be a node document this schema already accepts. That is the build instruction: disk, network, access, sysexts, update channel, and the AI pin. Unknown fields fail closed. A shell script, a `curl` target, or a field named like key material is rejected. "What gets installed" stays inside the Debian image policy.

After decrypt, the renderers run and exit. The next boot uses the document. If the document names DHCP, the lease remains. If it names a static address, `blunix-net` renders that and the bootstrap lease is not kept.

TLS authenticates the name. The passphrase authenticates the document. A compromised portal can replace the ciphertext. It cannot produce a new document that decrypts under a passphrase it does not hold.

A GitHub release is a later place to publish a signed image artifact. It is not how v1 obtains the node document, and no fetch script exists. Signature checks that are designed and not built: the UKI under Secure Boot, the image signature beside the artifact, the node-document signature (who signs it is still open), and the vendor CLI digests in section 5.

### 7. Blunix Log

Updating an image is a new row in an append-only log, then a sysupdate manifest generated from that log. The running host does not download the website. Its node document already names an update URL and a channel. systemd-sysupdate reads the manifest at that URL, installs into the other slot, and the previous slot still boots.

A row holds the version, the channel, the artifact sha256, the signature, the predecessor on that channel, and the file names (qcow2, raw, manifest). Publishing a version does not rewrite an older row. Withdrawing a bad image is a new row that points at the version and drops it from the generated manifest. The bytes of a withdrawn artifact can stay on the file server so a machine already mid-update can still finish or roll back. They are absent from the manifest a new boot will follow.

`POST` of a log row is a publisher scope on the API. An ordinary account key cannot append one. The public site renders the log. `GET` of the log is public. The manifest at `https://updates.blunix.io/blunix` (the URL in the test node document) is produced from the rows whose channel is current. It is not edited by hand.

A republished build config and a new image are different events. The config changes the next install that fetches that label. The image changes machines that already named that channel.

## Success Criteria

The spike is done when all of these are true on a developer laptop:

- `mkosi qemu` reaches a login on a Debian 13 image with a signed UKI.
- A second build, differing by one package, is applied by sysupdate and the previous slot still boots.
- On the regular profile, the default running units fit on one screen: sshd, systemd-networkd, time sync, containerd. Speech, BRLTTY, Orca, and Emacspeak are not in that list.
- The update test never invokes apt on the running VM.
- An SBOM and a signature sit next to the image artifact, even if the signing key is a test key.
- `blunix-disk render cloud-vm` emits repart drop-ins mkosi accepts. First boot on a larger disk grows `/var` and leaves the ESP and root slots where the image put them.
- `blunix-net render dhcp-any` gets a lease. `static-single` brings up an address. Neither path edits a file by hand on the VM.
- Both renderers reject a model that contains a private key, passphrase, or unknown field.
- A node document that names the disk model, the network model, and an access profile is the only per-host input required to boot.
- Menu keys 1 through 5 select the five access profiles. `console-speech` with `speakup.synth=dummy` speaks the login prompt on the dummy channel. `regular` does not load Speakup. `large-print` sets the 32-cell font. A missing sound card does not stop boot. Orca does not start unless the graphical sysext is installed.
- The UKI contains no Grok, Claude, or Codex binary. With `ai: default` and `enabled: true`, first boot links the three pinned binaries under `/var/lib/blunix/ai` after the checksum matches. `blunix-ai disable` leaves that directory empty. A wrong digest links nothing, and sshd still comes up. No unit starts the CLIs.
- When bootstrap is in the spike: a wrong passphrase leaves the machine on the DHCP lease and applies no document. A right passphrase yields a node document `blunix-node` accepts. The passphrase does not appear in the HTTP request. A file that is a shell script is rejected.

## Distribution Plan

v1 distribution is a qcow2 and a raw disk image plus a sysupdate manifest on a static file server. The manifest is generated from the Blunix Log. A new image is a new row. The file server does not rewrite an old row to change what a channel installs. No ISO, no cloud marketplace listing, no public apt repository. CI builds the image with mkosi from a pinned Debian snapshot and fails if the snapshot float changes without a commit. Cloud marketplace images (AMI, Azure, GCP) wait until the rollback test has been boring for a while.

## Dependencies

- mkosi, systemd-boot-efi, and a Debian snapshot pin.
- A UEFI qemu (edk2) for the secure boot experiment.
