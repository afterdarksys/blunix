Designed, not built

The log we are building

GitHub releases are how images ship today. The design adds an append-only Blunix Log on top: one row per version and channel, holding the artifact digest, the signature, and the version it replaces. None of this is running.

  1. The log is the source

    A publisher appends a row through the API. An ordinary account key cannot. The public page is a rendering of those rows. An old row stays where it was written.

  2. The manifest is generated

    systemd-sysupdate reads a manifest at the update URL. That file is produced from the current rows for the channel. Nobody edits it by hand.

  3. Mirrors are caches

    A row can name more than one https mirror, and GitHub release assets are one of them. The machine checks the digest. A mismatch is refused, and the running image stays. The build is on the platform page.

  4. The other slot boots

    The new image installs beside the one that is running, and the previous slot still boots. That is how the host lands on its feet.

  5. A withdrawn version leaves the manifest

    Withdrawing appends a row. The old row remains, so you can see that it shipped and that it was pulled. A new boot does not select it.

Config is the other pipe

An image is a release. The build document for one machine is ciphertext on a label, such as https://ada.blnx.io/. Republishing a label changes the next install from it. It does not rewrite a machine that already applied a document.

  • Next install. A new publish replaces what the next install from that label will decrypt. The build hosts are built and tested, not deployed.
  • Already installed. Taking a new document on a running machine is the job of the service client, which is designed, not built.

The account that registers a label is on the account page. The routes are on the API page.
