Check it yourself

Verify a release

A signed release carries SHA256SUMS.asc, a detached signature over SHA256SUMS. Check the signature first, then the files.

  • The key. Blunix Release Signing, sign-releases@blunix.io. OpenPGP, ed25519. It expires on 1 October 2028. Download it from blunix.io/keys/blunix-releases.asc. The same file is keys/blunix-releases.asc in the source repository, so you can check one against the other.
  • The fingerprint. 62F7 36BE A2AB 2E1F A16D 5138 BCB3 426C 090A DF92. Compare all of it. A short key ID is not enough.
  • Step 1. Import the key: curl -fsSLO https://blunix.io/keys/blunix-releases.asc, then gpg --import blunix-releases.asc.
  • Step 2. Check the signature: gpg --verify SHA256SUMS.asc SHA256SUMS. It must say the signature is good and name the fingerprint above. Anything else, stop.
  • Step 3. Check the files: sha256sum -c --ignore-missing SHA256SUMS. Every file you downloaded must say OK.

v0.1.0 is an unsigned test release, so it has no SHA256SUMS.asc. For it, only step 3 applies.

How releases are built

Built in one place, signed in another

Official images come from a dedicated build server. Signing happens somewhere else.

  • Signed tags only. The build server builds git tags of afterdarksys/blunix that are signed by the pinned release key. An unsigned or lightweight tag is refused.
  • Pull only. It checks GitHub every 10 minutes. Nothing on the internet can connect to it, apart from restricted admin access.
  • No keys on the build server. It holds no signing key. Its only credential can write to one staging bucket. Builds there expire after 30 days.
  • Signed offline. The maintainer pulls a build from staging, checks it, signs SHA256SUMS with the release key, and publishes the GitHub release.
Designed, not built

The log we are building

GitHub releases are how images ship today. The design adds an append-only Blunix Log on top: one row per version and channel, holding the artifact digest, the signature, and the version it replaces. None of this is running.

  1. The log is the source

    A publisher appends a row through the API. An ordinary account key cannot. The public page is a rendering of those rows. An old row stays where it was written.

  2. The manifest is generated

    systemd-sysupdate reads a manifest at the update URL. That file is produced from the current rows for the channel. Nobody edits it by hand.

  3. Mirrors are caches

    A row can name more than one https mirror, and GitHub release assets are one of them. The machine checks the digest. A mismatch is refused, and the running image stays. The build is on the platform page.

  4. The other slot boots

    The new image installs beside the one that is running, and the previous slot still boots. That is how the host lands on its feet.

  5. A withdrawn version leaves the manifest

    Withdrawing appends a row. The old row remains, so you can see that it shipped and that it was pulled. A new boot does not select it.

Config is the other pipe

An image is a release. The build document for one machine is ciphertext on a label, such as https://ada.blnx.io/. Republishing a label changes the next install from it. It does not rewrite a machine that already applied a document.

  • Next install. A new publish replaces what the next install from that label will decrypt. The build hosts are live.
  • Already installed. Taking a new document on a running machine is the job of the service client, which is designed, not built.

The account that registers a label is on the account page. The routes are on the API page.
